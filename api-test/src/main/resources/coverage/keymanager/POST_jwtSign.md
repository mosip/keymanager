**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Signs a JSON document and returns it as a JSON Web Token-style signature (JWS). Other MOSIP services use it to sign responses and credentials with a key held by the key manager, so receivers can check the data came from MOSIP and was not changed. With no application ID it signs with the key manager's own signing key (KERNEL / SIGN).

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "dataToSign": "eyJhbnlLZXkiOiJUZXN0IEpzb24ifQ",
    "applicationId": "",
    "referenceId": "",
    "includePayload": true,
    "includeCertificate": true,
    "includeCertHash": false,
    "certificateUrl": ""
  }
}
```
`dataToSign` (base64url-encoded JSON) is required. `applicationId`/`referenceId` choose the key; empty means KERNEL/SIGN. The `include...` flags add the payload, the certificate (`x5c`), the certificate hash (`x5t#S256`) or a certificate URL (`x5u`) to the token.

On success:
```json
{
  "response": { "jwtSignedData": "eyJ4NWMi...", "timestamp": "2026-11-10T10:00:00.000Z" },
  "errors": null
}
```
Failures come back in `errors[]`, e.g. `KER-JWS-108` (caller may not use this app's key), `KER-JWS-103` (data is not JSON), `KER-KMS-012` (no key yet), `KER-KMS-020` (signing not allowed for that app/reference pair), `KER-KMS-005` (missing field).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. An app's key policy can further limit which user names may sign with its keys. See README.md § How authentication works in this module.
