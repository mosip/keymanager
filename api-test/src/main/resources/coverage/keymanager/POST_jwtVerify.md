**About this endpoint**

**What this endpoint does**

Checks a JSON Web Signature (as made by jwtSign or jwsSign) and says whether it is genuine: that it was made by the expected key and that the data has not been changed. Optionally it also checks that the signing certificate chains up to a trusted authority for a given partner domain.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "jwtSignatureData": "eyJ4NWMi....",
    "actualData": "",
    "applicationId": "",
    "referenceId": "",
    "certificateData": "",
    "validateTrust": false,
    "domain": ""
  }
}
```
`jwtSignatureData` is required. `actualData` is the base64url data for a token signed without its payload. The verifying certificate is taken, in order, from the token's own `x5c` header, from `certificateData`, or from the key named by `applicationId`/`referenceId` (KERNEL/SIGN when empty).

On success:
```json
{
  "response": { "signatureValid": true, "message": "Validation Successful", "trustValid": "TRUST_NOT_VERIFIED" },
  "errors": null
}
```
A signature that does not match is not an error: `signatureValid` is false and `message` is `Validation Failed`. `trustValid` is `TRUST_NOT_VERIFIED`, `TRUST_NOT_VERIFIED_NO_DOMAIN`, `TRUST_CERT_PATH_VALID` or `TRUST_CERT_PATH_NOT_VALID`. Errors include `KER-JWS-106` (unreadable token), `KER-JWS-105` (could not verify), `KER-JWS-107` (certificate expired or not yet valid), `KER-KMS-002` (unknown app ID) and `KER-KMS-005` (missing field).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.
