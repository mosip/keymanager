**What this endpoint does**

Protects pieces of a resident's personal data (name, date of birth, ...) with "zero knowledge" encryption. Each value is locked with a key built from the resident's own ID (UIN or VID) plus one of many random keys the key manager keeps, so the stored data is useless to anyone who does not also know whose data it is. MOSIP services use it to keep resident data unreadable in caches and databases; `zkDecrypt` reverses it with the same resident ID.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "id": "<resident UIN or VID>",
    "zkDataAttributes": [
      { "identifier": "fullName", "value": "Ravi Kumar" },
      { "identifier": "dateOfBirth", "value": "1990/01/01" }
    ]
  }
}
```
`request.id` is required; it is never looked up, only used to build the key. `identifier` is a free label echoed back; `value` is the plain text to protect.

On success:
```json
{
  "response": {
    "zkDataAttributes": [ { "identifier": "fullName", "value": "<base64url encrypted value>" } ],
    "encryptedRandomKey": "<random key encrypted for the IDA PUBLIC_KEY certificate>",
    "rankomKeyIndex": "1234"
  },
  "errors": null
}
```
`rankomKeyIndex` (spelled that way on the wire) says which stored random key was used; `encryptedRandomKey` lets IDA recover that random key with its own private key. Failures come back in `errors[]`, e.g. `KER-KMS-005` (missing `id` or unreadable request). Several malformed attribute lists are currently accepted or give HTTP 500 (rows _006, _012-_014).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.

<summary>Technical details (automation + verification notes)</summary>

- Handler: `ZKCryptoManagerController.zkEncrypt` (ZKCryptoManagerController.java:62-71); roles from `mosip.role.keymanager.postzkencrypt` (application-local.properties:178).
- Service: `ZKCryptoManagerServiceImpl.zkEncrypt` (:207-238). Picks a random Active row of `keymgr.data_encrypt_keystore` (:286-293), unwraps it with the `KERNEL`/`IDENTITY_CACHE` master key (AES/ECB), derives the data key from SHA-256 of `request.id` (:330-342) and AES-GCM-encrypts each value with a fresh 12-byte nonce and 32-byte AAD.
