**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Version 2 of jwtSign: signs a JSON document and returns a JWS token, with two additions — the whole certificate chain can be put in the token header instead of only the signing certificate, and the caller can add its own header fields (for example `typ`). Used by credential-issuing services that need standard JWT headers.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "dataToSign": "eyJhbnlLZXkiOiJUZXN0IEpzb24ifQ",
    "applicationId": "",
    "referenceId": "",
    "additionalHeaders": { "typ": "JWT" },
    "includePayload": true,
    "includeCertificateChain": true,
    "includeCertHash": false,
    "certificateUrl": ""
  }
}
```
`dataToSign` (base64url-encoded JSON) is required; the other fields work as in jwtSign. A `kid` entry in `additionalHeaders` is not copied as-is: it becomes the prefix of the key ID.

On success:
```json
{
  "response": { "jwtSignedData": "eyJ0eXAi...", "timestamp": "2026-11-10T10:00:00.000Z" },
  "errors": null
}
```
Failures come back in `errors[]` with the same codes as jwtSign (`KER-JWS-108`, `KER-JWS-103`, `KER-KMS-012`, `KER-KMS-020`, `KER-KMS-005`).

**Who can call it**

The same roles as jwtSign: ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). An app's key policy can further limit which user names may sign with its keys. See README.md § How authentication works in this module.
