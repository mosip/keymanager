**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Registers a partner's own certificate (signed by the partner's CA) with MOSIP. The key manager checks that it chains up to a CA uploaded for the same partner domain and that it belongs to the stated organisation, then issues a MOSIP-signed copy of it (same key, signed by MOSIP's partner-signing PMS key) and stores both. The returned ID is what getPartnerCertificate and getPartnerSignedCertificate take.

**Request & response**

```json
{
  "id": "string", "version": "string", "requesttime": "2026-11-10T10:00:00.000Z", "metadata": {},
  "request": {
    "certificateData": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
    "organizationName": "Partner Org",
    "partnerDomain": "AUTH"
  }
}
```
`organizationName` must equal the certificate's `O` value exactly. On success:
```json
{
  "response": {
    "signedCertificateData": "<URL-safe base64 p7b: MOSIP-signed partner certificate, PMS, ROOT>",
    "certificateId": "7a6b5c4d-....",
    "timestamp": "2026-11-10T10:00:01.000Z"
  },
  "errors": null
}
```
For the `FTM` domain (by default) the p7b holds the partner's own chain instead. Failures come back in `errors[]` with HTTP 200, e.g. `KER-PCM-004` (expired), `KER-KMS-021` (less than 335 days left by default), `KER-PCM-015` (self-signed), `KER-PCM-006` (CA not uploaded for this domain), `KER-PCM-008` (organisation mismatch), `KER-PCM-013` (key below 2048 bits), `KER-PCM-014` (signature algorithm not allowed), `KER-PCM-011` (domain not allowed), `KER-KMS-013` (not a certificate), `KER-KMS-005` (empty field).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, PMS_ADMIN and PMS_USER (default configuration). Anyone else is refused. See README.md § How authentication works in this module.
