**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Turns personal data that was protected by `zkEncrypt` ("zero knowledge" encryption) back into plain text. Each value was locked with a key built from the resident's own ID (UIN or VID) and one of many stored random keys, so only a caller that supplies the same resident ID gets the data back. MOSIP services use this to keep resident data in caches and databases unreadable to anyone who does not know whose data it is.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "id": "<the resident UIN or VID used when encrypting>",
    "zkDataAttributes": [
      { "identifier": "fullName", "value": "<encrypted value returned by zkEncrypt>" }
    ]
  }
}
```
`request.id` is required and must be exactly the ID used at encryption time. Each attribute's `identifier` is just a label that is echoed back; `value` is the base64url text zkEncrypt returned.

On success:
```json
{
  "response": {
    "zkDataAttributes": [ { "identifier": "fullName", "value": "Ravi Kumar" } ]
  },
  "errors": null
}
```
Failures come back in `errors[]`: `KER-ZKC-004` (wrong ID or damaged value), `ZK-DEC-001` (value too short), `KER-CRY-003` (value not base64), `KER-KMS-005` (missing `id`). Some bad inputs currently give HTTP 500 `KER-KMS-500` (rows _005, _010).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.

<summary>Technical details (automation + verification notes)</summary>

- Handler: `ZKCryptoManagerController.zkDecrypt` (ZKCryptoManagerController.java:86-94); roles from `mosip.role.keymanager.postzkdecrypt` (application-local.properties:179).
- Service: `ZKCryptoManagerServiceImpl.zkDecrypt` (:241-283). Encrypted value layout (decoded): 4-byte big-endian key index, 12-byte GCM nonce, 32-byte AAD, then AES-GCM ciphertext + 16-byte tag. The index selects a row of `keymgr.data_encrypt_keystore`, whose key is unwrapped with the `KERNEL`/`IDENTITY_CACHE` master key (AES/ECB) and then combined with SHA-256 of `request.id` to derive the data key (:330-342).
- Nested attribute fields are not bean-validated (no `@Valid` on ZKCryptoRequestDto.java:38), so blank `identifier`/`value` reach the service.
- Decrypted bytes are turned into text with the JVM default charset (:425; zkEncrypt uses the same at :221) — UTF-8 on Java 18+ unless `file.encoding` is overridden.
- Needs the ZK random-key store populated by the keys-generator job (the legacy sheet's "Run key generator job").
- `crypto_integrity` was added to this file's categories for AC-5 flow F4 (row _009).
