**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Signs any piece of data and returns it as a COSE_Sign1 message — the compact, binary (CBOR) signature format used where JSON tokens are too large, for example in QR codes and offline credentials. The receiver can check with `/coseVerify1` that the data came from MOSIP and was not changed. With no application ID it signs with the key manager's own signing key (KERNEL / SIGN).

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "payload": "eyJhbnlLZXkiOiJUZXN0IEpzb24ifQ",
    "applicationId": "",
    "referenceId": "",
    "algorithm": "",
    "protectedHeader": { "includeCertificate": true },
    "unprotectedHeader": {},
    "includeCOSETag": true
  }
}
```
`payload` (base64url-encoded bytes, any content) is required. `applicationId`/`referenceId` choose the key; empty means KERNEL/SIGN. `algorithm` overrides the one picked from the reference ID. The header maps may ask for the certificate (`includeCertificate`), the whole chain (`includeCertificateChain`), the certificate hash (`includeCertificateHash`), a certificate URL, a `kid`, or any custom header. `includeCOSETag` = false leaves out the COSE_Sign1 tag.

On success:
```json
{
  "response": { "signedData": "d28445a101390100a0...", "timestamp": "2026-11-10T10:00:00.000Z" },
  "errors": null
}
```
`signedData` is the COSE message as a lower-case hex string. Failures come back in `errors[]`, e.g. `KER-KMS-005` (missing payload), `KER-CRY-003` (payload not base64url), `KER-JWS-108` (caller may not use this app's key), `KER-KMS-012` (no key yet), `KER-KMS-020` (signing not allowed for that app/reference pair).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN, RESIDENT and CREDENTIAL_ISSUANCE (default configuration). Anyone else is refused. An app's key policy can further limit which user names may sign with its keys. See README.md § How authentication works in this module.
