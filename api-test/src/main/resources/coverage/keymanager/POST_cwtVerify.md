**About this endpoint**

**What this endpoint does**

Checks a CBOR Web Token (CWT) made by `/cwtSign`: is it a real CWT, is it currently valid (not before its start date, not after its expiry), do the issuer and subject match what is expected, and was it signed by the expected key without changes? Optionally it also checks the signing certificate's trust chain.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "coseSignedData": "d83dd28445a101390100a0...",
    "applicationId": "",
    "referenceId": "",
    "certificateData": "",
    "issuer": "mosip.io",
    "subject": "mosip.io",
    "validateTrust": false,
    "domain": ""
  }
}
```
`coseSignedData` (the hex string from `/cwtSign`) is required. The key is found as for `/coseVerify1`: a certificate inside the token, else `certificateData`, else `applicationId`/`referenceId` (empty means KERNEL/SIGN). `issuer`/`subject` override the configured expected values.

On success:
```json
{
  "response": { "signatureValid": true, "message": "Validation Successful", "trustValid": "TRUST_NOT_VERIFIED" },
  "errors": null
}
```
A wrong signature gives `signatureValid` = false and `Validation Failed`. Failures come back in `errors[]`, e.g. `KER-KMS-005` (missing data), `KER-CWS-111` (not a CWT), `KER-CWS-112` (no COSE_Sign1 inside), `KER-SIG-115` (not yet valid), `KER-SIG-116` (expired), `KER-SIG-118` / `KER-SIG-119` (issuer or subject missing / not matching), `KER-KMS-012` (no key yet).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN, RESIDENT and CREDENTIAL_ISSUANCE (default configuration). Anyone else is refused. There is no per-app key policy check: verifying uses only public certificates. See README.md § How authentication works in this module.
