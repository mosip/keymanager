**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Creates a secret (symmetric, AES) key inside the key manager's hardware security module for a given application and reference ID — for example the key another MOSIP service uses to encrypt its cached data. The key itself never leaves the key manager; the call only reports whether a key was created or already existed. With `force` set, the current key is retired and a new one created.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "applicationId": "KERNEL",
    "referenceId": "IDENTITY_CACHE",
    "force": false
  }
}
```
`applicationId` and `referenceId` are required. `force` is meant to be optional, but leaving it out currently fails (row _006).

On success:
```json
{
  "response": { "status": "Generation Success", "timestamp": "2026-11-10T10:00:00" },
  "errors": null
}
```
`status` is `Generation Success` when a new key was made and `Key Exists.` when a current key was already there. Failures come back in `errors[]`, e.g. `KER-KMS-005` (missing field or unreadable request), `KER-KMS-003` (more than one current key).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.
