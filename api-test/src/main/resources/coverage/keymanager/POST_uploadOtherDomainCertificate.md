**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Stores the certificate of a key that belongs to another system (another "domain", such as a partner), so that the key manager can encrypt data for that system or check its signatures. The key manager never holds the private key for these certificates — only the certificate. Sending a newer certificate for the same application and reference ID replaces the old one, which is kept as expired.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "applicationId": "PARTNER_APP",
    "referenceId": "partner-123",
    "certificateData": "-----BEGIN CERTIFICATE-----\n..."
  }
}
```
All three fields are required; `referenceId` must not be empty.

On success:
```json
{
  "response": { "status": "Upload Success", "timestamp": "2026-11-10T10:00:00" },
  "errors": null
}
```
Failures come back in `errors[]`, e.g. `KER-KMS-005` (missing field), `KER-KMS-013` (not a readable certificate), `KER-KMS-031` (KERNEL + SIGN is reserved), `KER-KMS-030` (reserved EC reference ID), `KER-KMS-034` (the key manager holds its own key there), `KER-KMS-035` (same certificate already current), `KER-KMS-032` / `KER-KMS-033` (inconsistent existing key data).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.
