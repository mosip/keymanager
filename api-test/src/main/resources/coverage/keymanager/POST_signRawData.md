**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Signs raw data with a key held by the key manager and returns the signature together with everything a receiver needs to check it: the signing certificate, a key ID and the algorithm name. It is the self-describing variant of signV2, used for example when building verifiable-credential proofs.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "dataToSign": "eyJhbnlLZXkiOiJUZXN0IEpzb24ifQ",
    "applicationId": "",
    "referenceId": "",
    "responseEncodingFormat": "base64url",
    "signAlgorithm": "PS256"
  }
}
```
`dataToSign` (base64url) is required; the other fields work as in signV2 (default output `base58btc`).

On success:
```json
{
  "response": {
    "signedData": "Qm9ndXM...",
    "keyId": "aBcD...",
    "certificate": "-----BEGIN CERTIFICATE-----\n...",
    "signatureAlgorithm": "PS256",
    "timestamp": "2026-11-10T10:00:00.000Z"
  },
  "errors": null
}
```
Failures come back in `errors[]` with the same codes as signV2 (`KER-JWS-108`, `KER-KMS-036`, `KER-KMS-012`, `KER-KMS-020`, `KER-KMS-005`).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN, RESIDENT and CREDENTIAL_ISSUANCE (default configuration). An app's key policy can further limit which user names may sign with its keys. See README.md § How authentication works in this module.
