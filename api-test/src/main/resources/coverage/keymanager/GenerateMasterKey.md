**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Creates (or returns) the master key pair of an application in the MOSIP key manager — the key every other key of that application is later tied to. The caller names the application and asks for either a signed certificate or a certificate signing request (CSR) for the key. The first call for an application generates the key pair (signed by the platform's ROOT key); later calls return the existing key unless the caller explicitly forces a new one, which retires the old key.

**Request & response**

The path ends in the object type wanted: `CERTIFICATE` or `CSR`. The body uses MOSIP's standard envelope:
```json
{
  "id": "io.mosip.keymanager.generateMasterKey",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "applicationId": "PMS",
    "referenceId": "",
    "force": false,
    "commonName": "www.mosip.io",
    "organizationUnit": "MOSIP-TECH-CENTER",
    "organization": "IITB",
    "location": "BANGALORE",
    "state": "KA",
    "country": "IN"
  }
}
```
`applicationId` is required and must have a key policy. `referenceId` must be empty, except `SIGN` for the `KERNEL` application. `force` = true replaces the current key. The subject fields are optional; missing ones take the service's configured defaults.

On success the response carries either `certificate` (for `CERTIFICATE`) or `certSignRequest` (for `CSR`), both PEM text, plus `issuedAt`, `expiryAt` and `timestamp`:
```json
{
  "response": {
    "certificate": "-----BEGIN CERTIFICATE-----\n...",
    "certSignRequest": null,
    "issuedAt": "2026-11-10T10:00:00",
    "expiryAt": "2029-11-09T10:00:00",
    "timestamp": "2026-11-10T10:00:00"
  },
  "errors": null
}
```
Failures come back in `errors[]`, e.g. `KER-KMS-002` (no key policy for the app ID), `KER-KMS-005` (invalid request), `KER-KMS-010` (reference ID not allowed).

**Who can call it**

Administrative and platform-service users: ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (the default configuration). Anyone else is refused. See README.md § How authentication works in this module.
