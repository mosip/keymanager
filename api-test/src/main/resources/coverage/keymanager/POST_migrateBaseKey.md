**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Part of the one-time move from an old key manager to a new one. It copies one "base" key (an application key under a reference ID, e.g. a partner's or a module's encryption key) into the new key manager: its certificate, its validity dates and its private key, still encrypted by the old master key. The new key manager files it under the application's current master key so that data encrypted under the old key can still be handled after the switch.

This changes the key store permanently. It is meant for an isolated migration environment and must never be mixed into a normal test run; run it last.

**Request & response**

```json
{
  "id": "string",
  "version": "string",
  "requesttime": "2026-11-11T10:00:00.000Z",
  "request": {
    "applicationId": "REGISTRATION",
    "referenceId": "10001_10002",
    "encryptedKeyData": "<private key, encrypted by the old master key>",
    "certificateData": "-----BEGIN CERTIFICATE-----\n...",
    "notBefore": "2024-01-01T00:00:00.000Z",
    "notAfter": "2026-01-01T00:00:00.000Z"
  }
}
```
On success:
```json
{ "response": { "status": "Migration Success", "timestamp": "2026-11-11T10:00:00" }, "errors": null }
```
If the same certificate is already stored for that app ID and reference ID, the status is `Migration Not Allowed. Valid Key Exists.` (still HTTP 200, no error). Errors: `KER-KMS-005` blank field, `KER-KMS-003` the app has no master key, `KER-KMS-013` certificate cannot be read.

**Who can call it**

Only users with the KEY_MIGRATION_ADMIN role (default configuration) — ordinary administrators are refused. See README.md § How authentication works in this module.
