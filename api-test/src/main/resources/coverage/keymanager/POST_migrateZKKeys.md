**About this endpoint**

<!-- ENDPOINT:details -->
**What this endpoint does**

Part of the one-time move from an old key manager to a new one. The zero-knowledge (ZK) data-encryption keys protect identity data; each has a numeric index. The old system wraps each key with the temporary certificate from `GET /getZKTempCertificate` and sends the list here. The new key manager unwraps each one with the temporary private key, re-wraps it with its own ZK master key and stores it under the same index. Each entry gets its own status. Optionally the temporary key is destroyed at the end.

This changes the key store permanently. It is meant for an isolated migration environment and must never be mixed into a normal test run; run it last.

**Request & response**

```json
{
  "id": "string",
  "version": "string",
  "requesttime": "2026-11-11T10:00:00.000Z",
  "request": {
    "zkEncryptedDataList": [
      { "keyIndex": 1, "encryptedKeyData": "<base64url, wrapped with the temporary certificate>" }
    ],
    "purgeTempKeyFlag": false
  }
}
```
On success:
```json
{
  "response": {
    "zkEncryptedDataList": [ { "keyIndex": 1, "statusMessage": "Migration Success" } ]
  },
  "errors": null
}
```
Per-entry status: `Migration Success`, `Error in Migration` (could not unwrap), `Migration Not Allowed. Valid Key Exists.` (index already used). Whole-call errors: `KER-KMS-003` no current temporary key or ZK master key, `KER-CRY-003` an entry is not base64.

**Who can call it**

Only users with the KEY_MIGRATION_ADMIN role (default configuration) — ordinary administrators are refused. See README.md § How authentication works in this module.
