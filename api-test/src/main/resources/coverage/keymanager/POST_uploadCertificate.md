**About this endpoint**

**What this endpoint does**

Replaces the certificate of a key the key manager already holds with one signed by an outside certificate authority. The usual sequence is: the key manager makes a key, `generateCSR` produces a signing request for it, a CA signs that request, and this endpoint stores the CA-signed certificate in place of the key manager's own. Only a certificate for the very same key pair is accepted. Use uploadOtherDomainCertificate instead for certificates of keys the key manager does not hold.

**Request & response**

```json
{
  "id": "string",
  "version": "1.0",
  "requesttime": "2026-11-10T10:00:00.000Z",
  "metadata": {},
  "request": {
    "applicationId": "REGISTRATION",
    "referenceId": "",
    "certificateData": "-----BEGIN CERTIFICATE-----\n..."
  }
}
```
`applicationId` and `certificateData` are required. An empty `referenceId` targets the application's master key; leaving the field out currently fails (row _006).

On success:
```json
{
  "response": { "status": "Upload Success", "timestamp": "2026-11-10T10:00:00" },
  "errors": null
}
```
Failures come back in `errors[]`, e.g. `KER-KMS-002` (no key policy), `KER-KMS-003` (no current key for that app ID and reference ID), `KER-KMS-013` (not a readable certificate), `KER-KMS-014` (certificate is for a different key), `KER-KMS-005` (missing field or unreadable request).

**Who can call it**

ZONAL_ADMIN, GLOBAL_ADMIN, INDIVIDUAL, ID_AUTHENTICATION, TEST, REGISTRATION_ADMIN, REGISTRATION_SUPERVISOR, REGISTRATION_OFFICER, REGISTRATION_PROCESSOR, PRE_REGISTRATION_ADMIN and RESIDENT (default configuration). Anyone else is refused. See README.md § How authentication works in this module.
